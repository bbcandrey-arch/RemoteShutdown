# Безопасность и модель угроз

## Заглушка опасных действий

`windows-agent/src/RemoteShutdown.Agent.Core/Power/PowerActionsService.cs`,
свойство `SimulateDangerousActions` (по умолчанию `true`).

**Почему она есть:** во время разработки тестовый таймер (`delaySeconds: 10`),
созданный через реальный подписанный HTTP-запрос, действительно выполнил
`shutdown.exe` и выключил рабочий компьютер пользователя. После этого
случая все опасные действия (shutdown/restart/sleep/hibernate/lock) заменены
на запуск `calc.exe` — так тестируется весь путь запроса (HMAC-подпись,
pairing, обработка на агенте) без риска реального выключения.

**Правило:** `SimulateDangerousActions` переключать в `false` только на
одноразовой тестовой машине/ВМ, которую не жалко перезагрузить случайно.
**Никогда** не выключать эту заглушку на рабочем ПК пользователя без явной
просьбы.

## Модель угроз

Целевой сценарий защиты: посторонний в той же Wi-Fi сети (сосед, гость,
взломанное IoT-устройство в той же подсети) не должен иметь возможность
управлять ПК.

- **Транспорт**: HTTPS с самоподписанным сертификатом. Центра сертификации
  нет — вместо цепочки доверия используется fingerprint pinning
  (`TlsPinningClient` в Flutter, `badCertificateCallback`).
- **Первое подключение — TOFU (Trust On First Use)**: при `pair/init`
  клиент ещё не знает отпечаток сертификата агента и принимает любой,
  запоминая увиденный. Это единственный момент, когда теоретически возможна
  MITM-атака — окно уязвимости открыто ровно на время ввода PIN пользователем.
  Смягчение: PIN нужно вводить физически рядом с ПК (виден на экране), плюс
  PIN проверяется на стороне агента с хэшем PBKDF2 (210 000 итераций).
- **Все последующие подключения — strict pinning**: сохранённый отпечаток
  сертификата должен совпасть побайтово, иначе запрос отклоняется. Это
  защищает от подмены ПК тем же именем/IP после сопряжения.
- **Аутентификация команд**: каждый запрос после pairing подписывается
  `HMAC-SHA256(sharedSecret, method + "\n" + path + "\n" + timestamp + "\n" + nonce + "\n" + body)`,
  секрет никогда не передаётся повторно по сети. Заголовки:
  `X-Client-Id`, `X-Timestamp`, `X-Nonce`, `X-Signature`.
- **Anti-replay**: сервер отклоняет запросы с уже виденным `nonce` (окно кэша
  nonce — 60 секунд) — это основная защита от повтора запроса. `timestamp`
  дополнительно должен быть не старше 3 минут — намеренно не строже: ПК без
  NTP-синхронизации (источник времени "Local CMOS Clock" вместо интернет-сервера)
  может незаметно "уплыть" на пару минут от реального времени, и при 30-секундном
  окне это молча обрывало все подписанные запросы с корректно синхронизированного
  телефона без внятной причины на экране (баг-репорт, см. docs/user-guide.md,
  "Решение проблем"). Рекомендуется всё равно держать автосинхронизацию времени
  включённой на ПК (Настройки → Дата и время).
- **Хранение секретов**:
  - На телефоне — `flutter_secure_storage` (Android Keystore-backed).
  - На ПК — SQLite, `sharedSecret` каждого сопряжённого устройства
    зашифрован через DPAPI (`DpapiProtector`), привязан к профилю
    пользователя Windows.
  - PIN на ПК проверяется через PBKDF2-хэш (`SettingsStore.Keys.PinHash`).
    Отдельно хранится DPAPI-защищённая копия PIN в открытом виде
    (`SettingsStore.Keys.PinPlainProtected`) — **только** чтобы показать его
    в окне настроек трея (пользователю нужно вводить PIN на телефоне, а
    хэш восстановить нельзя). Использует отдельную DPAPI-"цель"
    (`DpapiProtector.ProtectPin`/`UnprotectPin`), отличную от секретов
    устройств, — расшифровать один блок как другой не получится. Как и всё
    остальное в SQLite, эта копия читаема только из-под того же Windows-
    пользователя/машины (DPAPI `LocalMachine` scope).

## Известные незакрытые риски (см. также roadmap.md)

- ~~Нет UI отзыва сопряжённых устройств~~ — закрыто: вкладка "Устройства"
  в `RemoteShutdown.Agent.Tray` (см. architecture.md).
- **Нет rate-limiting на ввод PIN** — теоретически возможен брутфорс PIN,
  если атакующий успевает поймать `pair/init` до легитимного пользователя.
  Планируется ограничение попыток + блокировка pairing на время после N
  неудач.
- **Нет локального подтверждения опасных команд на экране ПК** — команда
  shutdown/restart выполняется (с учётом заглушки — "выполняется") сразу
  после проверки подписи, без дополнительного диалога на самом ПК. Пока
  единственная защита — необходимость пройти pairing.
- **QR-код пейринга ещё нет** — сейчас fingerprint и PIN вводятся вручную,
  что увеличивает риск опечатки/фишинга (пользователь может ввести PIN не
  того устройства). QR закрывает и это, и удобство одновременно.
