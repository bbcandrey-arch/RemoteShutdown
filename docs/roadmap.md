## Сделано с прошлого прохода

- [x] **QR-код пейринг (MVP)**: Windows Agent при старте генерирует и
      сохраняет `pairing-qr.png` (host+port, через `QRCoder`) рядом с БД,
      путь выводится в консоль. Flutter: кнопка "Сканировать QR-код"
      (`mobile_scanner`) на экране сопряжения подставляет host+port в форму
      — PIN пользователь всё равно вводит вручную (двухфакторность
      сохранена, см. security.md).
      **Не сделано ещё**: QR с полезной нагрузкой host+port+fingerprint+
      одноразовый pairing-токен, чтобы PIN не нужно было вводить вообще —
      актуально для пейринга без физического доступа к клавиатуре ПК.
- [x] **Offline-очередь действий с таймерами**: `PendingActionsQueue`
      (shared_preferences) на телефоне — `scheduleShutdownIn`/`cancelTimer`/
      `snoozeTimer` при сетевой ошибке кладут действие в очередь вместо
      потери; `refresh()` при восстановлении связи автоматически
      проигрывает накопленное; баннер "Ожидает отправки на ПК: N" в UI.
      ПК (SQLite) остаётся единственным источником истины по самим
      таймерам.
- [x] **Tray-приложение с UI настроек** (`RemoteShutdown.Agent.Tray`,
      WinForms): единственная видимая часть агента для пользователя —
      раньше PIN/порт/тестовый режим настраивались прямой правкой SQLite.
      Запускает `RemoteShutdown.Agent.Api.exe` как дочерний процесс.
      Три вкладки:
      - **Сопряжение**: QR-код, выбор сетевого интерфейса (если их
        несколько — Wi-Fi/Ethernet/VPN, `NetworkInfoService.GetAllIPv4Addresses()`),
        IP/порт текстом, установка/просмотр текущего PIN (PIN хранится
        для показа отдельно от хэша — DPAPI-защищённая копия,
        `DpapiProtector.ProtectPin`/`UnprotectPin`, отдельная "цель"
        от секретов устройств).
      - **Устройства**: список сопряжённых, отзыв доступа
        (`PairedDeviceStore.Revoke`).
      - **Общие**: порт, тестовый режим (`SettingsStore.Keys.TestMode` —
        теперь персистентная настройка, `PowerActionsService` перечитывает
        её при каждом вызове, переключается без перезапуска агента),
        автозагрузка при входе в Windows (`AutostartService`, ключ реестра
        HKCU\...\Run).
      Запуск: `RemoteShutdown.Agent.Tray.exe` (иконка в трее) или
      `RemoteShutdown.Agent.Tray.exe --settings` (сразу открыть окно).
      Проверено: 23/23 юнит-теста (включая новые DPAPI/network), реальный
      запуск на этой машине — окно и QR-код рендерятся, `test_mode`
      корректно инициализируется в живой БД.

## В работе / следующее (по приоритету)

### 1. Discovery (mDNS + UDP broadcast) + автопереподключение при смене IP
- Windows: `Makaretu.Dns.Multicast` — публикация `_pcshutdown._tcp.local`.
- Flutter: пакет `multicast_dns` для основного discovery + собственный UDP
  broadcast fallback (`DISCOVER_REQUEST`/`DISCOVER_RESPONSE`) на случай,
  если роутер режет mDNS.
- `ReconnectFlow`: при неудаче по сохранённому IP — сначала resolve
  `<hostname>.local`, затем UDP broadcast, сверка найденного устройства по
  `clientId`/fingerprint (не по имени), тихое обновление IP в
  `shared_preferences`.

### 2. Мониторинг и уведомления

- [x] **Уведомления в трее + журнал задач**: `TaskLogStore` (новая таблица
      `TaskLog` в SQLite) пишет запись при каждой прилетевшей с телефона
      команде питания и при создании/отмене/переносе/срабатывании таймера
      (`CommandEndpoints`, `TimerSchedulerService`). Трей поллит новые
      записи каждые 3 сек (общая БД с Api, отдельный IPC-канал не
      понадобился) и показывает `NotifyIcon.ShowBalloonTip` для каждой;
      вкладка "Журнал" в настройках показывает последние 200 записей.
      Громкость в журнал сознательно не пишется — слишком шумное событие.
      **Не сделано**: живые метрики по WS на телефоне (см. ниже) — это
      отдельная задача, журнал в трее её не заменяет.
- WS `/events` как `StreamProvider` на клиенте — живые метрики на dashboard.
- `flutter_local_notifications` — уведомления о срабатывании/отмене
  таймера, потере связи с ПК, ошибках команд.

### 2b. Несколько сопряжённых ПК

- [x] **Android-клиент умеет держать сколько угодно сопряжённых агентов
      одновременно**, не только один. `DeviceProfileStore` (было — один
      профиль в shared_preferences) переписан на список профилей + указатель
      "последний использованный"; `SecureStorageService` хранит sharedSecret
      по одному на `clientId` (было — один общий ключ); `PendingActionsQueue`
      тоже на `clientId` (было общая на всё приложение) — иначе offline-
      действия одного ПК при следующем подключении ушли бы другому.
      `DashboardController`/`dashboardControllerProvider` переведён на
      `.family<String>` по `clientId` — у каждого сопряжённого ПК свой
      независимый контроллер.
      Новый экран **"Мои ПК"** (`features/pc_list`, иконка в AppBar
      Dashboard) — список всех сопряжений, переключение, переименование,
      отзыв конкретной пары, кнопка "Добавить ПК" (снова экран сопряжения,
      без потери уже сопряжённых). При запуске приложение сразу открывает
      Dashboard **последнего использованного** ПК (без экрана выбора, чтобы
      не тратить время в типовом случае одного ПК) — при отвязке текущего
      ПК указатель автоматически переезжает на другой оставшийся, если он
      есть.
- [x] **Настройка переименования ПК**: локальное имя ПК на телефоне
      (`DashboardController.rename`/`PcListScreen`, иконка карандаша в
      AppBar и пункт меню в списке) — не трогает сам ПК, только то, как его
      подписывает конкретный телефон.
- [x] **Имя ПК передаётся в QR по имени машины в системе**: на агенте новая
      настройка `SettingsStore.Keys.DeviceName` (по умолчанию
      `Environment.MachineName`, редактируется в SettingsForm → "Общие" →
      "Имя ПК"), зашивается в `PairingQrService.PairingQrPayload.deviceName`
      и дополнительно возвращается полем `agentName` в ответе `/pair/init`
      — телефон подставляет его сразу при первом сопряжении что через QR,
      что вручную по IP. Заодно найден и исправлен смежный баг: раньше
      заголовок Dashboard показывал не имя ПК, а имя телефона ("Android
      Phone", это поле для другой цели — как ПК подписывает устройство в
      своём списке "Устройства"). Проверено: изменение "Имя ПК" в трее
      сразу перегенерирует QR с новым именем; агент на реальной машине
      верно проинициализировал `device_name` из `Environment.MachineName`.
      **Важно**: формат хранения профилей на телефоне сменился (список
      вместо одного профиля, секрет — по clientId) — на телефонах, где
      приложение уже было сопряжено до этого обновления, потребуется
      пересопряжение один раз.

### 3. UX опасных команд и управление доступом
- [x] Трей-иконка на Windows с UI: список сопряжённых устройств, кнопка
      "Отозвать", смена PIN без ручной правки SQLite — см. выше,
      "Tray-приложение с UI настроек".
- [x] **Баг отзыва доступа**: отзыв устройства в трее ("Устройства" → "Отозвать")
      не долетал до телефона — приложение зависало на Dashboard с ошибкой,
      без пути назад. Исправлено: сервер уже возвращал `UNKNOWN_CLIENT` для
      отозванного/неизвестного `clientId` (это было верно и раньше), но
      `DashboardController` не различал эту ошибку от обычной сетевой —
      теперь при `UNKNOWN_CLIENT` автоматически чистит профиль/секрет/
      offline-очередь и возвращает на `PairingScreen`. Плюс кнопка
      "Отвязать ПК" в Dashboard для ручного разрыва. Заодно оба провайдера
      (`pairingControllerProvider`, `dashboardControllerProvider`) переведены
      на `.autoDispose` — без этого повторный вход на Dashboard после
      разрыва тут же получал протухшее `PairingSuccess`/`unpaired` состояние
      от прошлого сопряжения. Проверено на реальном Android-телефоне.
- Rate-limiting на попытки ввода PIN при pairing.
- Опциональное локальное подтверждение (диалог на экране ПК) перед
  выполнением shutdown/restart, даже если запрос уже прошёл проверку
  подписи — по желанию пользователя, отключаемо в настройках.
- Показ PIN только с явным раскрытием ("Показать"/"Скрыть") — сделано;
  остаётся подумать про автоскрытие через N секунд, чтобы не оставался
  виден на экране случайно (сейчас скрывается только вручную).

### 4. Android-виджет на рабочий стол
- `home_widget` + нативный `AppWidgetProvider` (Kotlin) — статус ПК +
  пресеты 15/30/60 мин + Shutdown без открытия приложения.
- Headless background callback берёт секрет из `flutter_secure_storage`,
  переиспользует `ReconnectFlow` и уже реализованную offline-очередь —
  если ПК недоступен в момент тапа по виджету, действие тоже должно
  уходить в неё, а не теряться.

### 5. Windows Service (опционально, отдельный этап)
- Перенос ядра в `Microsoft.Extensions.Hosting` + `UseWindowsService()` для
  работы без входа пользователя в систему; tray-companion общается со
  службой через named pipe (lock/сессионные действия требуют доступа к
  рабочему столу пользователя — Session 0 isolation).
- Установщик (Inno Setup/MSI), автозапуск.

## Не начато, но зафиксировано в исходном плане

- Полноценный тест Wake-on-LAN (выключить ПК физически → разбудить с
  телефона magic-пакетом) — сейчас код клиента ещё не написан.
- Тест "перезапустить агент при активном таймере" на реальном железе — сама
  функциональность восстановления реализована и покрыта юнит-тестом
  (`TimerSchedulerServiceTests`), но не проверена вручную end-to-end после
  реального рестарта процесса агента.
- Тест смены IP (переключение подсети/новая DHCP-аренда) с проверкой, что
  `ReconnectFlow` находит ПК без участия пользователя — заблокирован до
  реализации пункта 3.

## Важное напоминание на будущее

`SimulateDangerousActions` должен остаться `true` на этой машине. Флаг
переключать в `false` только на отдельной одноразовой тестовой ВМ, когда
понадобится проверить, что реальные вызовы `shutdown.exe`/
`SetSuspendState`/`LockWorkStation` работают корректно — и то делать это
осознанно, не в рамках рутинного тестирования остального функционала.
